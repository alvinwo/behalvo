# Monitored actions

A monitored action is standing, owner-reviewed authority for one narrow effect.
It is not a model instruction, recurring approval, or permission to choose a new
effect later. The shipped operational path is synthetic only.

## Exact review and activation

The paired owner first creates the fixed synthetic fixture and proposes a grant.
Review shows the immutable adapter/version, connection generation, browser
profile, owner/work binding, one-effect maximum, inclusive Beijing date window,
eligible times, earliest-selection rule, exact group/identity/terms digests,
expiry, and the server-owned polling limits. The synthetic limits are:

| Limit | Reviewed value |
| --- | ---: |
| Observation freshness | 60 seconds |
| Poll interval | 2 seconds |
| Jitter | up to 250 ms |
| Request budget | 30 per 60 seconds |
| Failure backoff | 2 to 60 seconds |
| Maximum effects | 1 |

Activation requires a purpose-bound one-use arm token from that exact review,
plus the grant digest and revision. An ordinary action approval/execution token,
chat text, model output, timer, fixture ID, or browser message cannot arm standing
authority. A lost arm response is recovered through the durable request receipt;
it does not arm twice.

## Runtime behavior

One service owns the journal/store, queue, scheduler, worker, monitor service, and
browser session. A due poll performs read-only complete pagination. Missing,
drifted, stale, or incomplete evidence cannot narrow scope. Candidate selection
uses the reviewed deterministic policy. The selected page is reread before any
reservation.

If the candidate disappears during that read-only reread, the observation is
labelled `candidate_disappeared_before_reservation`. No action, allowance
reservation, intent, selection, submit gesture, or provider mutation exists. A
later poll may inspect a distinct candidate. Once reservation occurs, recurrence
stops atomically and the exact execute job is admitted on the same durable queue.
A failed or unknown reserved attempt never releases the one-effect allowance.

Before mutation the runtime rechecks the grant, action, attempt, connection,
installation, service claim, browser epoch, work revision, candidate evidence,
identity, full roster, terms, appointment absence, and expiry. Encrypted intent
is journaled before selection/submission. Success requires an exact confirmation
and authoritative appointment readback. Replay/rebuild only reduces journal
records and cannot poll, gesture, dispatch, or repair orphan effects.

## Owner controls and status

The paired loopback API and UI expose setup, proposal, exact review/arm, list and
detail, pause, human takeover, explicit resume, revoke, and stop. Status separates
queued, active, paused, blocked, verified, and stopped states. A timer by itself
does not mean monitoring is active.

Challenges pause durably and revoke the automation epoch before human takeover.
Resume queues a new read-only preflight. Manual booking, roster/identity/terms
drift, stale installation, connection drift, interrupted resume, or ambiguous
handoff stays fail-closed. Unknown submission outcomes use readback only and are
never automatically retried.

## Current boundary

Implemented evidence covers the local synthetic portal, compiled extension
scripts in a fake DOM/Chrome host, framed native transport, encrypted storage,
paired owner controls, restart, one booking/readback, stopped recurrence, and
effect-free rebuild. It is not installed Chrome or native-host evidence.

Live monitoring still requires owner-laptop read-only discovery, current portal
terms and group semantics review, final origin/page/polling contracts, a private
connection, installed signed helper and extension/native host, real profile
custody, independent security/architecture review, live acceptance, and a new
exact owner activation. No live grant can be created with the shipped defaults.
